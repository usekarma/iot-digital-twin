# Project Brief

## Business problem

Operations teams responsible for physical equipment need a simple way to observe equipment condition remotely and recognize abnormal motion or vibration without manually inspecting each asset. This project will use a physical M5Stack Core2 for AWS device as a stand-in for an industrial asset and connect its real telemetry to an AWS digital-twin representation.

The initial problem is intentionally narrow: prove that telemetry generated by a real device can move securely through AWS IoT services and become observable as the state of a digital twin.

## Desired outcome

Create a working vertical slice in which a physical M5Stack Core2 for AWS publishes IMU-based telemetry over MQTT/TLS to AWS IoT Core, the telemetry is made available to an AWS IoT TwinMaker digital twin, and a user can observe the current condition of the modeled asset.

The first release is a prototype, not a production monitoring platform.

## Users / stakeholders

- Primary user: engineer or operations analyst evaluating remote equipment condition.
- Business owner: project owner evaluating whether the digital-twin pattern is useful enough to continue.
- Technical owner: repository maintainer.
- Downstream consumers: future dashboards, alerts, analytics, or condition-monitoring services.

## Current process

There is no integrated monitoring workflow today for this demonstration asset. Device state must be observed directly from the physical device or through ad hoc development tooling.

The project will establish a repeatable path from physical telemetry to cloud-side digital-twin state.

## Constraints

- Security/compliance: device-to-cloud traffic must use authenticated encrypted transport. Credentials and private keys must never be committed to Git. Device permissions should follow least privilege and be scoped to required MQTT topics/actions.
- Cost: keep the prototype intentionally small and avoid unnecessary always-on infrastructure. Record expected recurring AWS costs before production-style deployment.
- Latency/SLA: prototype target is that newly published telemetry becomes observable in the cloud within 10 seconds under normal development conditions. This is an experiment target, not a production SLO.
- Data volume: one physical device publishing low-rate telemetry. Initial target is no more than one telemetry message per second.
- Deployment environment: AWS development/sandbox account only until a human explicitly approves any broader deployment.
- Existing systems that cannot change: M5Stack Core2 for AWS hardware (model K010-AWS) and AWS IoT Core are the initial device/cloud boundary.

## Inputs

Initial device telemetry will be derived from the Core2 IMU and device metadata. The proposed event shape is:

```json
{
  "device_id": "core2-aws-001",
  "timestamp": "2026-10-08T19:45:00Z",
  "accel_x": 0.03,
  "accel_y": -0.02,
  "accel_z": 1.01,
  "gyro_x": 0.4,
  "gyro_y": 0.1,
  "gyro_z": -0.2,
  "operating_state": "NORMAL"
}
```

Exact units, sampling behavior, and derived-condition logic must be specified before implementation claims are made.

## Outputs

- Authenticated MQTT telemetry accepted by AWS IoT Core.
- A modeled digital-twin entity representing the physical device or represented asset.
- Current telemetry/condition visible through the TwinMaker data model or associated visualization.
- Deterministic validation of telemetry shape and condition classification in repository tests.
- Evidence describing what was deployed, how it was verified, and what remains unproven.

## Failure expectations

- Invalid or incomplete telemetry must be rejected or clearly quarantined rather than silently treated as valid state.
- Loss of network connectivity must not corrupt the digital-twin model.
- Duplicate telemetry must not create duplicate irreversible side effects.
- Cloud-side processing failures must be observable through logs/metrics during the prototype.
- A failed authorization attempt must not be retried by broadening permissions automatically.
- No agent or CI workflow may deploy, mutate, or destroy AWS infrastructure without explicit human authorization for the concrete operation and target.

## Out of scope

The first vertical slice will not attempt to provide:

- predictive maintenance or machine-learning anomaly detection
- fleet-scale device management
- production alerting/on-call integration
- a polished 3D industrial scene
- multi-device tenancy
- firmware OTA management
- production availability guarantees
- automatic remediation of physical equipment

These can be evaluated only after the basic telemetry-to-digital-twin path is demonstrated.

## Success metrics

The prototype succeeds when:

- the physical Core2 establishes an authenticated TLS connection to AWS IoT Core
- valid IMU telemetry is received using the documented topic and message contract
- the represented asset's latest condition is observable through the TwinMaker/SiteWise data path within 10 seconds for at least 95% of a controlled 20-message demonstration
- malformed telemetry is deterministically rejected by application/domain validation
- moving or shaking the physical device causes an observable telemetry change in the digital-twin view
- no device credentials, certificates, private keys, or AWS secrets exist in Git history
- repository quality checks pass for implemented software
- deployment evidence identifies the exact AWS account/region/resources used
- a human explicitly reviews and approves any cloud mutation before it is executed

## Discovery and experiment

- Hypothesis and smallest stakeholder demo: if a real Core2 device can securely publish its IMU telemetry and that telemetry can be observed as the state of a TwinMaker-modeled asset, then the architecture is credible enough to evaluate for richer industrial condition-monitoring use cases.
- Current baseline and measurable target: baseline is no integrated cloud digital twin; target is one real device with a repeatable end-to-end telemetry path and observable state change within 10 seconds for at least 95% of a controlled 20-message demonstration.
- Assumptions with validation owner and deadline: confirm the exact Core2 firmware/toolchain, AWS Region, telemetry units, TwinMaker/SiteWise integration path, and expected prototype cost before cloud deployment. Technical owner is responsible for validation before implementation is called complete.
- Prototype decision: iterate / stop / harden only after the first stakeholder demonstration and recorded feedback.
- Data classification and permitted synthetic fixtures: device telemetry only; no personal/customer data. Synthetic telemetry may be used for automated tests, but a real-device demonstration is required for the prototype outcome.
- Production owner and release decision maker: human project owner. AI agents may prepare implementation, plans, tests, and evidence but cannot authorize production release or AWS mutation.

## Initial architecture hypothesis

```text
M5Stack Core2 for AWS
        |
        | MQTT over TLS / X.509 device identity
        v
AWS IoT Core
        |
        | telemetry routing / ingestion
        v
AWS IoT SiteWise (initial preferred time-series/model source)
        |
        v
AWS IoT TwinMaker
        |
        v
Twin state / dashboard / scene
```

AWS IoT TwinMaker currently provides first-party integration with AWS IoT SiteWise, so SiteWise is the initial preferred telemetry/model source for the experiment. The Architect pass should challenge whether that is the smallest useful implementation before infrastructure is added.

## Human decision points

Human review is required before:

1. provisioning AWS resources for the experiment
2. creating or attaching device certificates/policies beyond a reviewed least-privilege design
3. enabling service integrations or IAM roles
4. introducing recurring-cost resources
5. changing from a development/sandbox target to any broader environment
6. destroying resources or deleting retained telemetry
7. claiming the prototype is production-ready

The agent may propose these actions and prepare code, plans, commands, and evidence. It may not treat those artifacts as authorization.

Use `specs/` for detailed contracts and `docs/prototype-review.md` for observed feedback.
